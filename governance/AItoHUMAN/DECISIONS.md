# RootSound 决策记录（人话版）

## D-2026-10-29-structure-gpu · 本地模型接入 GPU——当前实验范围

用户明确要求接入 GPU，授权为此安装项目内所需运行组件；不扩大为修改其他工具、全局
Python 或显卡驱动。在本机 Intel Arc 上使用单独的 PyTorch／torchaudio2.7.1+xpu 与
锁定的官方 Intel 依赖，校验下载，保留原 CPU 库及权重；检查模型参数、输入与返回张量
实际位于所选设备，保持 float32。

测速后用户明确选择使用 CPU，因此所有模型执行入口及方法窗口默认 CPU；默认打开
方法窗口也不初始化／检测 GPU。GPU 与 GPU优先的自动模式仍可主动选择。

方法窗口为 Demucs 提供自动（GPU优先）／严格GPU／CPU；显示检测及实际设备，部分
算子由 CPU 协同时说明。自动可在 GPU 失败后改用 CPU 跑同一模型并明确原因；严格GPU
失败必须报告，不伪装为 GPU。取消／关闭终止工作进程并清理未完成文件，保留现有分析
和原件。其他四种传统方法仍用 CPU。

GPU可用不代表更快：本机30秒受控混音，CPU15.69秒、GPU21.51秒，估计声部最大RMS
差异2.04e-8；混合精度更慢且偏差更大，未采用。这些是特定输入下的测量，不保证所有
歌曲的速度，也不是实际音乐听感验收。

## D-2026-10-29-structure-methods · 多种分解原理与选择窗口——当前实验范围

用户认为首次分解效果难以满意，要求多实现几种其他原理，并用小窗口选择心仪的方法。
这不代表验收原 NMF 的分离效果。具体方法属于本次实现选择：本机已有 Hybrid Demucs
模型（鼓／贝斯／人声／其他残余）、中值 HPSS（持续／打击）、有界非相邻近邻中值
（REPET-SIM 思路的重复／变化）、双声道 Mid/Side（中央／侧边）和原 NMF（可请求2～8层）。
它们是不同机制，不是几个 NMF 预设。

分解、重新分解、进一步分解均可打开方法窗口；重新分解始终处理原输入，替换当前声部，
上一结果及沉默状态可撤销恢复；进一步分解仅替换选中父层。不适用的声道／缺失组件／
剩余层数在窗口说明，不暗中回退其他算法。模型使用已有组件及校验后的本地权重，工作
进程禁用网络，不自动安装／下载。保持分窗有界处理、完整帧数／采样率／声道、互补重建、
取消和原件保护。模型仍可能串音或归错电子音色；真实音乐听感与偏好待用户试听选择。

## D-2026-10-29-tone-structure · 音色结构与同步声音层——当前实验范围

用户要求新增类似合并音色器的工具：将打磨页换成总频谱／分解页，接收歌曲截取／EQ 传来的
长片段，分解成上下对齐的图，同步播放、独立激活／沉默，可拖播放头、进一步分解、撤销。
用户明确要**同时发生的声音层，不是前奏／主歌等时间分段**，各层不能重复包含完整原声；
图为**频率—音量，随播放时间变化**，因此另设共享时间条定位。

首次实现选择（已由上方多方法补充扩展）：独立“音色结构.exe”，按学习到的重复／相似非负频谱模板和互补掩码分配声音，
初次最多4层，进一步分解选中的父层并用子层替换；全部激活时总和重建输入，原声对照互斥。
结果按结构层中性命名，不承诺准确乐器分轨或完全没有串音。
本次会话保留、主动导出声部／混合 WAV、最多16当前层和8步分解撤销、磁盘缓存与取消处理
均为实现选择；新片段在提示后替换分析。主工作站目标与范围不变。

## D-2026-10-29-tone-processor · 独立音频加工工具“音色器”——当前实验范围

## D-2026-10-29-4 · 手动保存与自由草稿——有效

用户明确拒绝乐句、乐曲自动保存，编辑要留出随时试写、放弃的草稿空间；普通编辑不能覆盖
正式工程文件，“保存”和Ctrl+S必须是真实的确认动作。
用户进一步确认分层：乐句保存先加入当前工作工程，乐曲保存才统一写入文件；乐句保存不
独立落盘，也不能顺带保存尚未确认的歌曲编排。

新乐句未保存不进入正式库；离开有改动的乐句时可保存、放弃或继续编辑。放弃会真实恢复
已保存音乐字段，或删除未发布新稿，库只显示已确认元信息。退出项目、关闭窗口时可保存／
放弃／取消；保存乐曲或另存工程不能偷带未提交的乐句／音色编辑。确认移除乐句也是工作
工程中的修改，等保存乐曲后才正式落盘。

RB81采用原生内存工作快照、草稿显式归属歌曲及关闭前整理输入。创建、导入、另存副本和
库内明确的文件改名／删除仍是独立的显式操作；此次不删除或追溯改写已有用户工程。

## D-2026-10-29 · 行控制块自由斜向拖动——有效

## D-2026-10-22-2 · 上下级组织，同级自由交流 — 生效中

最高指挥中心负责整体组织和调度，不执行具体音乐工作。平行模块按任务
分工，内部需要时再设部门及更小单位；具体音乐工作由最次级单位执行，
没有下级的单位自己就是执行单位。

同级遵守共同上级制定的交流规范，在规范内自由交流，**不需要上级批准、
安排或转发每一次交流**。上级管规范不等于逐次审批。不能私设另一套语言，
也不能依赖对方内部实现；模块内部同理。

模块可以变化，功能可以重叠。一个下级同时有两个上级属于特殊情况，
等真遇到不可回避的需要再说。候选模块包括：采样获取、音色制作、乐句
谱写、歌曲编排、后期处理、界面渲染、引导共创、用户账号、创意工坊、
AI 智创和公共素材与工程管理；名单尚未冻结。

原因：清楚的职责边界让各单位专精和替换，同时不让用户承担内部协调。
纪律：最高中心不变成发声引擎，也不中转每一段声音或每一次消息。公开
端点、跨层交流细节和声音执行归属还需要验证，草案里已经标成建议或待定。
