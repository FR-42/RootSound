本轮新增
1. 补全工作者边界
Ripper托管入口 → HitnMixLibCLR.x64.dll原生初始化/状态检查 →
RipperFiles.dat字段读取 → PCM读取 → 原生工作线程 → 分析线程 → 峰/谐波阶段。
该DLL内嵌原生分析，并非只是管理外壳。任务记录0x758字节、标记0x01234567，
实际分析分支受配置影响；不能把反汇编中的call列表误写成无条件顺序。
见 native-worker-boundary.txt；八份直接Ghidra导出保留在worker-decompiled/。

2. 明确多窗口峰分析
主EXE326880在两种窗长上分析PCM，较长窗口只补充220Hz以下峰。
有效输入窗为N/2N，变换缓冲为2N/4N；主帧hop H与缓存对齐max(H,N/4)不同。
H从PCM索引推导为样本数；N、H、采样率初始化默认值尚未完全追溯。
这说明不能简单换成任意固定STFT参数后称为相同算法。

3. 补全谐波时序的数据含义
0x28对象存储分谐波轨迹，带组ID、起始分析索引及0x5c序列；
0x3c18候选记录分解为0xD8头部+48×0x13c谐波信息。
已核对缺口插值、活动轨迹索引、频率容差、分组强度查询和邻近候选调度。
第一处容差经汇编确认为0.5半音且至少6Hz；另一处是配置相关规则。
后续细化产生频率、两路相位和幅度；低幅度清零、近邻干扰处理及迭代重排
均与通用MIDI转录器不同。这些轨迹依然不能直接命名为最终音乐音符。
详见 native-temporal-followup.txt。

4. 已产生可执行原生算法重建模块
reconstructed_pitch_math.py重建36c990初始基频和36c2d0谐波伸展拟合。
通过真实汇编补齐fmaf第三参数、MAX而非MIN频率约束、单/双精度边界、
两轮求解和回退逻辑；常量字节保留在pitch-fit-constants.json。
已运行受控数值不变量检查；没有加载或执行RipX。
尚未原程序差分验证，因此仅作为静态推导模块保存，没有作为完整识别器接入EXE。
源码和说明也复制到应用的native-reconstruction目录，供后续实现复用。

GPU适配实测（与核心复原分开计）
本机Intel Arc已通过PyTorch2.7.1+xpu实际四/六轨前向和应用工作流验证，
输出设备为xpu。FP32神经网络在GPU，STFT/逆STFT在当前版本回CPU。
同一7.8秒生成信号、同版本库、CPU4线程、每模型两次热运行中位：
四轨CPU4.512秒 / XPU0.720秒，6.27倍；六轨CPU2.922秒 / XPU0.716秒，4.08倍。
GPU/CPU输出最大绝对差分别5.48e-6、2.23e-5，非逐位相同。
首次四轨XPU9.24秒、CPU8.25秒，初始化使GPU首轮略慢。
应用8.2秒两窗完整任务（含进程/库/模型初始化、解码、写文件）四/六轨约15.37/14.68秒，
不能把热模型推理倍率当作整条流程或所有音乐的速度保证。
详细指标：应用目录gpu-validation.json、last-gpu-test.txt指向的results.json。
