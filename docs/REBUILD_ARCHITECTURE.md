# RootSound 新架构草案

创建：2026-10-22；更新：2026-10-23。状态：设计草案，单音色基础流程已开始实现；完整工作站尚未完成。

本轮重建以用户在 2026-10-22 对话中明确的目的和决定为依据。旧原型已独立归档到 `legacy/prototype/`，其代码、目录和技术选择是历史与参考。新项目允许全部重建，不要求维持旧数据结构、旧界面或旧工程兼容。

本文将内容分为三种状态：

- **已确认**：用户已经明确的目的或规则，后续实现需要遵守。
- **建议**：为了落实规则提出的设计，可在审阅和验证后调整。
- **待定**：尚未作出决定；不应被后续开发者当作默认定案。

本文是面向项目所有者的中文架构说明。正式决定与适用范围见 [治理记录](../governance/DECISIONS.md)，实施建议见 [重建计划](REBUILD_PLAN.md)，实际完成范围见[重建进展](REBUILD_PROGRESS.md)。文中阶段目标不自动代表已有功能。

第一阶段的进一步设计见[基础设计](REBUILD_FOUNDATION.md)。其中“声音运行”独立为后台平行模块及其主要分工已获用户批准；最小内容、交流能力和内部实现等细节仍是建议，待确认和验证。

## 1. 根本目的

**已确认：让普通人创作音乐的摩擦力为零。想创作什么音乐，甚至只是一段声音，都能够方便地表达、实现和继续修改。**

用户可能喜欢一首音乐并想仿制，可能脑中有独创旋律，也可能只需要一个音效。他可能没有乐理、编曲或熟练使用电脑的经验，不愿先经历繁杂学习和机械输入。

软件需要缩短“有想法”到“听见成果”之间的距离，并帮助没有明确想法的人探索。内部的专业能力可以复杂；用户当前面对的信息、步骤和术语应当与正在完成的任务相称。

结果既可以是一首歌，也可以是一个音色、一个音效或一段录音。制作一个声音不应被迫先建立完整歌曲。专业用户仍应能直接进入精细工具。

## 2. 创作入口与基本体验

### 2.1 欢迎与直接进入

**已确认：**

- 默认欢迎页只发出友好、简洁、有启发性的创作邀请，不暴露参数、内部结构和成排工具。
- 主要按钮暂用“开始旅途”一类文案，引导好奇但没有明确想法的用户。
- 不显眼但可找到的入口允许跳过引导、直接创作；不使用容易误解成关闭软件的“退出”。
- 有上次工程时，可提供“继续上次的项目”。
- 可以关闭欢迎页，并指定启动后直接进入某个模块的窗口。

“开始旅途”等是当前文案方向，最终措辞与视觉仍待设计。社区、账号提示和功能宣传不占据首次创作的注意力。

### 2.2 引导共创与精细编辑往返

**已确认：**

1. 用户可以通过描述、参考声音、语音或哼唱表达想法。
2. 旋律需要忠实记录，并可以迅速强化为可试听方案，例如更合适的音色、伴奏、低音和鼓组。
3. 每轮通常提供三四个方向，也可以在适合的情形下使用一根含义清楚的滑杆。普通描述与专业描述均可使用。
4. 多轮选择可逐渐缩小探索范围，推测用户倾向，激发灵感。
5. 对话用于粗略生成和方向探索；细调交给相关创作模块。
6. 精调后的内容可以带回对话，继续探索；最终成果可直接继续编辑。

**建议：**保留原始输入、候选方案和已选内容的关联。返回共创时明确使用哪份修改结果；后续生成的改动范围应可看清、比较和撤回。

**待定：**第一版采用何种旋律识别、候选生成和偏好推测方法，以及是否提供本地 AI。不能用只有混合音频的试听代替“可以继续编辑的音乐结构”，也不能把尚未接入的生成能力描述成可用功能。

### 2.3 品质要求

**已确认的方向：**界面简洁、直观、美观，主要创作对象清楚；乐句能直接摆放和拖动，包络可直接编辑图形，音符拖动有连续而明确的反馈。大众入口使用能激发直觉的词，旧术语“槽位、槽分、通道机架”等不自动继承为新界面名称。

具体界面与命名仍需设计。完整能力可从顶部入口找到；窗口管理是整理编辑空间的工具，不能代替创作流程本身的设计。

## 3. 组织结构

### 3.1 最高指挥中心

**已确认：**拥有最高的全局组织与调度职责，管理全局规则，不执行任何具体音乐工作。

**建议的职责：**组织模块的装配与运行、识别可用能力、协调全局任务及资源、维护顶层交流规范、协调启动与恢复。

声音合成、旋律识别、谱写、混音和音频处理必须由具体执行单位承担。不能以“公共核心”为名把这些功能重新集中到最高指挥中心。

### 3.2 模块、部门与执行单位

**已确认：**

- 顶层模块相互平行，各自完成明确任务。
- 模块可按实际需要设部门，部门还可继续细分。
- 执行具体音乐工作的永远是最次级单位；上级负责组织与协调。
- 没有下级的简单单位本身即可执行工作，不为了层级形式建立空部门。
- 模块允许增删、替换、拆分、合并，也允许功能重叠。
- 一个下级同时拥有两个上级是特殊情况，实际不可避免时再讨论；当前不实现相关机制。

组织上的上下级关系不决定声音必须依次经过哪些单位。两个模块具有相同处理能力，也不意味着必须提前抽取一个多上级的共享部门。

## 4. 交流规则

### 4.1 共同上级制定规范，同级自由交流

**已确认：**同级单位使用共同上级规定的强连通交流渠道。这里的“强连通”指能够通过共同规范开展所需交流，不要求每个单位主动依赖所有其他单位。

- 同级交流可以自行发起、持续进行，不需要上级逐次许可、安排或中转。
- 上级负责规范；上级不成为所有消息或声音数据的必经节点。
- 单位之间不私设另一套交流语言，不依赖对方的内部实现。
- 模块间遵守顶层规范；模块内部同级部门遵守其所属模块的规范，逐级类推。

全局调度职责不构成同级交流的额外审批条件。

### 4.2 最小交流内容

**建议：**共同规范至少表达以下内容，具体字段和代码形式在第一阶段验证：

| 内容 | 用途 |
| --- | --- |
| 能力与版本 | 让调用者知道一个单位公开提供什么，以及能否理解当前数据 |
| 请求与对应结果 | 明确做什么、作用于哪个对象，并把结果交回发起者 |
| 内容引用与修改状态 | 知道取得哪份内容，避免误用旧版本或覆盖别人已保存的修改 |
| 通知、进度、取消与失败 | 长任务可反馈、可中止，失败不假装完成 |
| 数据类型、时间与音高等单位 | 保证不同单位对同一份内容理解一致 |
| 持续的数据传输 | 支持录音、试听和实时处理，而不逐个音频采样点发送普通任务消息 |

统一规范可以容纳多种有明确含义的操作；不预先建设一个接受任意对象、任意脚本的万能消息框架。

### 4.3 跨模块与跨层级的边界

**建议，尚非用户定案：**跨模块使用公开的模块能力；模块可以将能力交给其最次级单位执行，也可以公开稳定的执行端点。外部不通过内部文件路径或任意部门地址穿透模块。内部层级变化时，公开能力尽量不受影响。

此处约束的是共同规范和公开边界，不要求消息逐层中转。是否公开下级端点、公开范围及扩展方式，列入第一阶段的协议验证。

## 5. 模块及主要职责

**清单以用户的初步设想为基础，模块名称、数量与拆分均可调整。声音运行独立为后台平行模块及其主要分工已获明确批准；其余模块仍按原先记录的确认范围处理。** 下表描述主要职责，不表示其他单位禁止拥有重叠能力。

| 模块 | 主要职责与成果 | 主要边界 |
| --- | --- | --- |
| 采样获取 | 从文件、麦克风、系统声音及未来其他来源获取音频素材 | 来源可以增加；采集实现通过相应执行单位提供，不要求其他模块懂设备协议 |
| 音色制作 | 编辑音频素材，或电子合成，产出可演奏、可复用的音色；支持单个声音的创作 | 内部声音生成与编辑方法可以多样；不把音符演奏内容固定装进音色 |
| 乐句谱写 | 使用多个音色，组织旋律、节奏和演奏，产出乐句 | 现有音符画布与步进功能可作为参考；不照搬旧 Pattern 拥有整套音色副本的结构 |
| 歌曲编排 | 使用多个乐句及需要的音频内容，组织时间位置，进行整体调整、混音和效果处理 | 乐句与歌曲的时间位置分别表达；编排轨道不固定等于某个乐句 |
| 后期处理 | 对作品作最终处理，产出普通音频文件或完整工程文件 | 可以接收有意义的单个声音输出请求，不要求先造一首歌曲；完整打包调用公共管理能力 |
| 界面渲染 | 全项目的界面显示、交互、入口与工作空间呈现 | 音乐内容的含义由相应业务单位解释；显示方式变化不应重写音乐算法 |
| 声音运行（独立后台模块已确认） | 全项目实际试听、播放、时间执行、设备输出与离线音频生成 | 全局声音的统一运行边界；创作含义与编辑由创作模块负责，处理方法具有明确实现归属；同级交流仍自由进行 |
| 引导共创 | 欢迎后的引导、粗略生成的交互、多轮候选试听与选择、精细编辑的移交和回接 | 不承担所有精细编辑；不是所有模块的必经入口 |
| 用户账号 | 用户身份及账号相关能力，支持偏好与作品的在线延续 | 本地创作不要求先注册或登录 |
| 创意工坊 | 用户交流、音乐与采样发布、发现和评价等 | 不占据首次创作入口；发布与本地保存分别表达 |
| AI 智创 | 提供 AI 理解、分析、生成等能力，支持可调整的接入方式 | 与引导共创分工；候选应带回后续编辑需要的结构或明确的能力限制 |
| 素材与工程管理 | 统一保管素材和工程，保存引用、依赖与相关状态，可按所有者单位整理 | 不代替业务单位解释或制作音色、乐句等内容 |

### 5.1 界面渲染与业务模块协作

**建议：**业务模块通过共同规范提供可显示状态、可执行操作及必要的专用编辑需求；界面渲染负责如何显示、怎样接收用户操作，并按规范调用能力。对业务内容的修改仍由相应单位处理，再提交公共管理部分保存。

不能让界面直接修改其他模块的内部对象。也不要求把所有未来编辑器挤进一种万能表单。专用绘图、音符编辑和实时交互怎样接入，需要通过一个真实编辑器验证后确定。

### 5.2 实时声音执行归属

**已确认的约束：**具体音乐工作在最次级单位执行，最高指挥中心不合成、不混音；同级持续传输不逐次申请许可。

**已确认：**独立、平行的“声音运行”模块统一承担试听、播放会话、时间执行、实际声音执行、设备输出和离线音频生成。用户将它类比界面渲染，定位为后台模块、“全局声音的海关”。这里的“海关”指实际发声与音频渲染的统一公开运行边界，各创作模块按共同规范接入；不改变同级自由交流规则。

创作模块保留各自的内容含义和编辑能力，具体处理方法具有明确实现归属。后台能力无需用户每次试听先打开一个额外窗口。内部部门、具体数据与接入方式仍待验证，见[基础设计](REBUILD_FOUNDATION.md#1-声音执行的归属)。

需要同时支持单音色独立试听、乐句试听、歌曲播放和最终导出。不能让试听一个音色必须创建歌曲，也不能让联网 AI 请求阻塞声音与界面。

## 6. 成果与工程内容

以下是**用于落实已确认规则的概念模型建议**，不是已冻结的数据结构。

| 对象 | 含义 |
| --- | --- |
| 原始录音 / 采样 | 获取到的原始声音及来源信息 |
| 声音素材 | 对录音选择、清理、转换或加工后的可用内容；是否单独设对象类型待定 |
| 音色 | 可响应演奏的声音配置，可引用采样，也可以由合成方法描述 |
| 乐器使用配置 | 某份工程如何使用某件音色，包括需要的工程内调整；确切对象形式待定 |
| 乐句 | 多个声音角色的演奏内容，含音符及时间、力度等信息 |
| 片段 | 乐句或音频内容在歌曲中的一次摆放，具有歌曲起点与播放范围 |
| 歌曲 | 片段的整体时间组织，以及混音、效果和其他歌曲级信息 |
| 工程 | 本次创作的完整工作内容及其依赖，可以服务于歌曲或单个声音等目标 |
| 共创会话 | 输入、候选、选择和编辑结果之间的上下文关系；精确保存范围待定 |

**建议：**乐器配置与乐句的演奏内容分别管理。复制乐句时不自动复制整套音色。乐句可以有不同长度，片段可以前后排列、重复使用及独立选择范围；编辑吸附不决定整个工程的唯一长度。

音高、精细偏移、时间、音符长度、速度变化和处理参数的最终表示仍待确定。旧实现的 MIDI 槽位、槽分、格数上限、四分之一格存储及全局圈长都不是新项目的自动约束。

## 7. 公共保管、所有者与编辑

### 7.1 保管与所有者

**已确认：**所有创作成果交给公共的素材与工程管理部分保管，可按所有者单位整理。

**建议：**

- 管理部分维护稳定的内容标识、保存状态、依赖关系、查找和恢复。
- 所有者单位负责相关专业含义、合法性检查与编辑能力，通过公开规范提供给其他单位使用。
- 按所有者分类是一种整理方式，不自动变成“只有所有者才能使用”的限制。
- 读取、编辑稿、保存结果和播放时读取的状态需要区分，避免多个模块各自维护互相争夺的权威副本。
- 模块卸载、重命名或升级后，已保存的内容不能跟着消失；重新归属、读取兼容与缺失能力提示的具体方案待定。

### 7.2 覆盖正在被引用的音色

**已确认：**制作中的工程引用公共管理部分的共享音色。覆盖被引用音色前需要警告后果，用户可以另存为新音色。

**建议的执行过程：**

1. 试调发生在编辑稿里，可试听；未确认保存前，不改变其他工程使用的共享版本。
2. 用户选择覆盖时，查找仍引用该音色的工程，说明受影响范围。
3. 用户可选择覆盖、另存为新音色或取消。
4. 覆盖保持共享音色的身份，引用它的工作工程采用更新后的保存内容。
5. 另存创建新身份，原引用继续使用原音色；当前工程是否切换到新音色应明确表达，不能悄悄更换其他工程。

引用检查应涵盖管理库中仍有引用的工程，而不仅是当前打开的窗口。已独立导出的完整工程文件不受库中覆盖影响。

**待定：**同一内容同时在多个编辑位置打开时的修改冲突、撤销和覆盖处理。不能因为界面单人使用就忽略这种情况，也不因此预先实现多人实时协作。

## 8. 两类导出与完整工程文件

### 8.1 两类成果

**已确认：**

| 导出类型 | 目的 | 使用条件 |
| --- | --- | --- |
| 普通音频 | 播放、传播和声音素材编辑 | 使用支持该音频格式的软件，不要求 RootSound；不包含原创作的全部结构 |
| 完整工程文件 | 跨设备继续编辑音乐或声音 | 需要兼容版本的 RootSound；不另找原设备素材、插件、账号或网络资源 |

制作中的工程使用共享引用。导出完整工程时，收集导出时的完整参数与全部依赖，形成独立的内容快照，即固定在导出时刻的一份可编辑内容。

### 8.2 打包与重新打开

**建议：**

- 后期处理提供导出操作，公共管理部分负责依赖收集、固定导出状态、保存和重新载入；具体音乐渲染由执行单位负责。
- 收集包含音色依赖采样等间接关系，不能只打包歌曲直接指向的第一层对象。
- 包内记录需要的结构、参数、音高解释、效果配置、素材与可读版本信息；不能保留只能回原库或联网取得的必要引用。
- “参数齐全”还需要相应执行方法可用。若允许第三方处理器，应明确怎样满足跨设备要求，不能只装入插件名称。
- 打开独立文件时避免与目标库的同名、同标识内容发生静默合并或覆盖；在库中怎样落地及何时允许显式复用，待定。
- 重建时不默认延续旧 JSON 的结构、扩展名或内嵌方式，也不承诺自动兼容旧工程。

**待定：**容器、扩展名、编码、压缩、大素材处理、校验、版本兼容，以及非内置算法的可移植方案。

## 9. 离线、联网与个人创作档案

**已确认：**绝大多数基础创作功能应可离线使用。在线 AI、账号、云保存与同步、素材发现、分享和交流可以逐步加入；这些能力不构成本地创作的必经入口。

个人创作档案指用户希望延续的审美偏好、创作习惯、常用素材和操作偏好。

**建议：**档案可本地保存，登录后选择同步；将明确设置与推测倾向分别记录，允许查看、修改和清除；长期偏好不覆盖当前作品的临时要求。

网络任务的等待或失败，应留在其工作范围内。已经落地并保存了完整内容的生成结果，应当能够继续离线编辑；是否提供离线生成、使用哪家服务以及具体账号体系，待定。

## 10. 技术组织建议

以下是**表达职责的一种目录示意，不是已选实现，更不要求现在创建全部目录**：

```text
app/                      最高指挥中心的装配、运行与全局调度
contracts/                顶层公共交流规范
modules/
  <module>/
    public/               该模块公开能力和它负责维护的内部交流约定
    <actual-units>/       按实际任务设置的部门或执行单位
tests/                    验证规范、模块协作、真实创作与界面操作
```

同级模块不通过导入兄弟模块内部文件形成依赖。具体交流可在同一进程发生，也可跨进程或网络；不预设模块必须是独立服务、独立程序或插件。

新项目不自动沿用“零运行时依赖”、浏览器独占、原生 DOM、单一 Store 和旧三层目录。**用户已确定 Windows 桌面软件优先**；桌面框架、安装方式、设备接入与第三方库仍需针对目标评估，目前未选定或安装新依赖。

第一条单音色流程暂用现有 TypeScript、浏览器音频和浏览器存储验证共同规范；这些是可替换的验证实现，不将最终工作站限定为浏览器软件。具体能力与边界见[重建进展](REBUILD_PROGRESS.md)。

### 10.1 当前目录与历史隔离

用户已要求将旧项目代码和文档移入子目录，并重新建立 Git 历史。新源码位于 `src/workstation/`，根入口、类型检查、测试和生产构建只面向新项目；旧原型的代码、样式、测试、说明与原治理记录位于 `legacy/prototype/`，具有独立启动入口。具体使用方式见[项目说明](../README.md#旧项目档案)。

旧原型 `model / audio / ui` 的分工可作为经验参考。任何复用都需要服从新边界，不能以“兼容原型”为理由让旧结构重新成为中心。归档文件不作为新项目的运行或构建依赖；新旧浏览器数据也没有自动转换。

## 11. 必须验证的创作流程

### A. 单个声音

直接进入音色制作 → 获取或生成一个声音 → 编辑并试听 → 保存 → 输出普通音频，或保留可编辑工程。过程中不强迫先建立乐句或歌曲。

### B. 乐句到歌曲

取得若干音色 → 谱写并试听乐句 → 重复使用或形成其他乐句 → 在歌曲中安排位置与整体处理 → 后期输出。音色内容、演奏内容和摆放位置能分别调整。

### C. 共创与细调往返

表达或哼出想法 → 忠实记录 → 试听少量强化方案 → 选择 → 将选中内容交给相关模块细调 → 把修改结果带回当前会话 → 继续探索或转为完整编辑。交接使用结构化创作内容，不要求用户导出再导入。

### D. 共享音色与独立工程

两个工作工程引用同一音色 → 试调时另一工程保持原状态 → 覆盖前列出影响 → 另存时旧引用保持 → 导出独立工程 → 在空库、离线环境重新打开编辑。随后修改原库，独立文件保持原内容。

## 13. 第一阶段的验收依据

先完成一条能真实制作、试听、保存和重新打开的流程，再扩大模块范围。阶段验收同时检查：用户是否能低成本完成任务、模块之间是否只依赖共同规范、内容是否完整且可恢复、界面与声音是否响应明确。

程序启动、类型检查或空模块注册通过，都不足以代表新工作站已经成立。哼唱、多轮共创、精细编辑和声音创作需要各自的实际体验验证。

**收拢：RootSound 以人的声音表达为中心。组织层级管理职责，公共规范连接独立单位，素材与工程管理维持成果连续性；用户可以自由进入、组合和往返创作任务。此草案固定已确认原则，对实现建议和未决问题保持可见，供后续逐项验证。**
